## Контекст

Наша команда разрабатывает «Учёт заявок на ремонт оборудования» (repair-requests) — сервис, в котором сотрудники подают заявки на ремонт, а инженеры АХО принимают и закрывают их, — в рамках курса "Управление конфигурацией бизнес-приложений".

**Характеристики проекта:**
- Размер команды: 4 человека (Анна Волкова — с 2026-10-13)
- Длительность проекта: 16 недель (1 семестр)
- Частота релизов: промежуточные демо на каждой практике (раз в 2 недели) + финальный релиз
- Опыт команды с переменными окружения, `.env`, pydantic: `os.environ` и `.env` — с практики №3 у всех; pydantic — модели запросов FastAPI видели все, `pydantic-settings` никто не использовал; python-dotenv Мария подключала в личном проекте
- Окружения проекта: `dev` — ноутбуки участников (Windows, macOS, Linux), стек в Docker Compose (`compose.yaml`) или приложение без Docker через `uv run`; `prod` — сервер в модуле 4 (пока гипотеза). Секреты `prod` знает только владелец репозитория (Иван) и тот, кто будет разворачивать

**Проблема:** конфигурация сейчас читается одной строкой `os.environ.get("DATABASE_URL")` прямо в `/health`; об отсутствии переменной приложение узнаёт только при запросе; остальные параметры зашиты в код. Нужно выбрать механизм конфигурации, способ различать `dev` и `prod` и защиту от попадания секретов в git (DoD, раздел 2).

## Рассмотренные варианты

| Критерий | A: `os.environ`, как сейчас | B: `pydantic-settings` | C1: python-dotenv + `os.environ` |
|---|---|---|---|
| Когда приложение сообщает, что обязательной переменной нет | При первом запросе к `/health` (`503`, `DATABASE_URL is not set`) | При старте: `ValidationError`, приложение не запускается | При первом обращении к `os.environ[...]`; при старте — только если проверку написать самим |

| Чтение `.env` при запуске без Docker | Нет, переменные задаются вручную | Да, `env_file=".env"` в настройках класса | Да, `load_dotenv()` |

## Решение

Мы выбрали **`pydantic-settings`** (вариант B).

**Механизм и окружения:**
1. Механизм: класс настроек на `pydantic-settings` — выиграл по критериям «когда сообщает об отсутствии переменной» (при старте), «типы» и «защита секретов от вывода в лог» (`SecretStr`)
2. Окружения: переменная `APP_ENV` со значениями `dev` и `prod` (по умолчанию `dev`). В `prod` выключаем `/docs` и отладку, все секреты обязательны и без значений по умолчанию
3. Значения `dev` — в `.env` у каждого разработчика (его читает класс настроек при запуске без Docker; в Docker значения передаёт `compose.yaml`). Значения `prod` — на сервере, вне git, задаёт владелец репозитория (Иван) при развёртывании (модуль 4)
4. Если обязательная переменная не задана — приложение не стартует и пишет, какой переменной не хватает

**Правила для секретов:**
1. Никогда не коммитятся `.env` и любые файлы с реальными паролями и ключами; `.env` уже в `.gitignore`
2. `.env.example` обновляется в том же PR, что и код, который читает новую переменную; в нём только заглушки (`changeme`)
3. Попадание секрета в git предотвращает gitleaks (v8.28.0) в pre-commit hook — запускается перед каждым коммитом у каждого участника (ставится на практике №4)
4. Если секрет всё-таки попал в коммит — историю не переписываем, секрет считаем скомпрометированным и сразу меняем (пароль БД — новый в `.env` у всех и `docker compose down -v`), в ADR записываем дату ротации

## Обоснование решения

**Почему мы выбрали именно этот механизм?**

1. **Проверка при старте:**
   Ошибка конфигурации видна сразу при `docker compose up` или `uv run`, а не на первом запросе к `/health`.

2. **Типы и секреты:**
   Таймаут подключения — `int`, `APP_ENV` — одно из двух значений, пароль — `SecretStr` и не попадёт в лог.

3. **Стоимость перехода:**
   pydantic уже стоит через FastAPI; добавляется один пакет через `uv add` (ADR 002) и один класс.

4. **Требования DoD курса:**
   Раздел 2: «`pydantic-settings` или аналог», минимум два окружения `dev` и `prod`, секреты не в git (вместе с gitleaks в pre-commit).
