# ADR 001: Выбор стратегии ветвления Git

## Статус
Предложено

## Дата

## Контекст

Наша команда разрабатывает «Учёт заявок на ремонт оборудования» (repair-requests) — сервис, в котором сотрудники подают заявки на ремонт, а инженеры АХО принимают и закрывают их, — в рамках курса "Управление конфигурацией бизнес-приложений".

**Характеристики проекта:**
- Размер команды: 3 человека
- Длительность проекта: 16 недель (1 семестр)
- Частота релизов: промежуточные демо на каждой практике (раз в 2 недели) + финальный релиз
- Уровень опыта команды с Git: Иван — уверенно, Мария — базово, Олег — базово
- Требования к стабильности `main`: высокие, т.к. проект оценивается преподавателем и другими командами

**Проблема:** Нам необходимо выбрать стратегию ветвления Git, которая позволит:
1. Параллельно работать над несколькими фичами без конфликтов
2. Обеспечить стабильность основной ветки
3. Соответствовать требованиям DoD курса (PR с approval, чистая история)
4. Быть посильной для нашей команды по уровню сложности

## Рассмотренные варианты

### Вариант A: GitFlow
**Суть:** Две долгоживущие ветки: `main` (релизы) и `develop` (интеграция). Фичи идут от `develop`, релизы — через `release/*`, срочные исправления — через `hotfix/*`.  
**Плюсы:**
- Чёткое разделение стабильного и интеграционного кода
- Предсказуемый процесс релизов с версиями

**Минусы:**
- Пять типов веток — много для команды из 3 человек
- `develop` и `main` расходятся, синхронизация — источник конфликтов

**Подходит ли нам:** Нет — релизов по расписанию нет, накладные расходы выше пользы.

### Вариант B: GitHub Flow
**Суть:** Одна долгоживущая ветка `main`, всегда рабочая. Каждое изменение — короткоживущая ветка от `main` и Pull Request обратно в `main` после ревью.  
**Плюсы:**
- Простая модель: одна база, один тип PR
- Каждое изменение проходит ревью через PR — прямо закрывает требования DoD

**Минусы:**
- Нет отдельной ветки для стабилизации релиза
- Незаконченная фича в `main` сразу видна всем — нужна дисциплина маленьких PR

**Подходит ли нам:** Да — соответствует размеру команды и частоте демо.

### Вариант C: Trunk-Based Development
**Суть:** Все коммитят в `main` очень часто (минимум раз в день), ветки живут часы; незаконченное прячется за feature flags.  
**Плюсы:**
- Минимум конфликтов слияния
- Быстрая обратная связь

**Минусы:**
- Требует CI и автотестов с первого дня — у нас их до модуля 3 нет
- Требует опыта с feature flags, которого у команды нет

**Подходит ли нам:** Нет — без CI и тестов `main` будет ломаться.

## Решение

Мы выбрали стратегию **GitHub Flow**.

**Схема ветвления:**

```
main:            ●──────────●──────────●──────────●
                  \        /  \       /  \       /
feature/version-   ●──●───●    \     /    \     /
endpoint:                       \   /      \   /
docs/adr-001-                    ●─●        \ /
branching-strategy:                          ●
bugfix/health-status:
```

**Правила работы с ветками:**
1. Ветка `main` всегда в рабочем состоянии
2. Каждое изменение — в отдельной ветке от `main`
3. Merge в `main` — только через PR с минимум 1 approval
4. Имена веток: `feature/...`, `bugfix/...`, `docs/...`
5. Сообщения коммитов — Conventional Commits

**Защита `main` (ruleset `protect-main`, Active, bypass пуст):**
- Restrict deletions — `main` нельзя удалить
- Block force pushes — историю `main` нельзя переписать
- Require a pull request before merging: Required approvals — 1; Dismiss stale pull request approvals when new commits are pushed; Require conversation resolution before merging
- Require status checks to pass — выключено до появления CI (практика №5)

## Обоснование решения

**Почему мы выбрали именно эту стратегию?**

1. **Соответствие размеру команды:**
   Трём участникам достаточно одной долгоживущей ветки: параллельно идут 2–3 PR.

2. **Частота релизов:**
   Демо раз в две недели показываем из `main`; отдельные релизные ветки не нужны.

3. **Уровень опыта команды:**
   У двух из трёх опыт базовый — одна база для всех веток снижает ошибки.

4. **Требования DoD курса:**
   PR с approval — центральный элемент GitHub Flow, требования DoD выполняются самой моделью.

## Последствия

### Положительные (+)
- Каждое изменение проходит ревью
- Простой для новичков процесс
- История `main` состоит из merge-коммитов PR

### Отрицательные (-)
- Нет буфера стабилизации перед демо
- Ожидание ревью может задерживать работу

### Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Конфликты при параллельных PR | средняя | среднее | Маленькие PR, `git merge origin/main` перед ревью |
| Нестабильный код попадёт в `main` | средняя | высокое | Ревью с локальным запуском по разделу «Как проверить» |
| Ревью задерживается | средняя | среднее | Срок ответа ревьюера — 24 часа |
| Настройки репозитория, включая защиту веток, может менять только владелец (@ivan-petrov); без него правила не поправить | средняя | высокое | Состав правил выписан в `CONTRIBUTING.md`, раздел «Защита ветки» — по нему защиту можно воссоздать; изменения настроек планируются на встречах, где владелец присутствует |
